# Онлайн-запись к врачам для медцентра «Лотос»

Стадия: **реализован дизайн v2** — запись пациента, личный кабинет и CRM регистратуры
по прототипам `docs/design/v2/` (ветка `feat/design-v2`). План, решения и что осталось
за пределами дизайна — [docs/15-plan-v2.md](docs/15-plan-v2.md). Договора нет.

Репозиторий приватный намеренно: в документах есть сведения о процессах клиники,
включая практику, которая не соответствует закону.

## Запуск

Нужны Node 22+, pnpm и Docker (PostgreSQL в контейнере, порт 55432).

```bash
pnpm install
cp .env.example .env.local
pnpm db:up
pnpm db:migrate
pnpm db:seed
pnpm dev
```

`db:seed` создаёт демо-клинику из прототипов: 12 врачей, записи на сегодня и завтра,
поступления для сверки, кабинет пациента с документами. Повторный запуск ничего не меняет.

| Что | Где | Вход |
|---|---|---|
| Запись к врачу | `/` | без входа; код из СМС — в логе сервера `[смс:лог]` |
| Личный кабинет | `/kabinet` | телефон `+7 900 123-45-67`, код — в логе сервера |
| CRM регистратуры | `/crm` | `admin@lotos.demo`, `senior@lotos.demo` (старший смены), `grishin@lotos.demo` (врач), пароль `lotos-demo` |
| Документы для пациента | `/dokumenty/predoplata`, `/dokumenty/soglasie-pd` | — |

В разработке оплата идёт через страницу-имитацию банка, СМС и чеки пишутся в лог.
В продакшене заглушки запрещены: конфигурация не запустится без настоящих адаптеров.

Проверки:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm test:db
pnpm build
```

`test:db` работает с базой `lotos_test` (адрес — `TEST_DATABASE_URL`) и сам применяет миграции.

## Где проект сейчас

Клиника ответила на 20 вопросов первого круга. Из ответов выяснилось главное:
расписание ведётся в 1С:Медицина, оплата подтверждается администратором вручную по
входящей СМС, чеки на предоплату не выдаются, врачи сами снимают приёмы.

Подготовлен отчёт об обследовании с пятью блокирующими вопросами
(`docs/pdf/discovery-report.pdf`).

Отчёт клинике не отправлялся, директор правовых выводов не видела.

15 сентября 2026 года получены ответы на блокирующие вопросы от Дмитрия, из его
знания клиники (`docs/09-answers-round-2.md`). Ожидается, что клиника **оставит
на сайте только оплату сразу**, бронь до 17:00 и наличные останутся по телефону;
директор это ещё не подтвердила. Касса и ОФД есть, деньги по ссылке приходят на
счёт клиники, ссылка оказалась статическим QR СБП. Решение принимает директор.
Сопровождение 1С берёт на себя команда, доступ через AnyDesk ближе к 19–20
сентября, протокол сеанса — `docs/10-anydesk-session.md`. Цифр по объёмам у
клиники нет, их предстоит снять из 1С.

**Самая дорогая часть проекта** — правило «время держится за пациентом, деньги
до 17:00» — на сайт не идёт. Это снимает единственное обоснование заказной
разработки, см. `docs/07-approach.md`.

## Рекомендация обследования (до решения строить своё)

Не писать систему с нуля. Взять готовый сервис записи с оплатой и кассой, свою
работу свести к странице на сайте, настройке и надстройкам. Заказная разработка
оправдана ровно в одном случае: если владелец не откажется от правила брони до
17:00.

Подробно и с оговорками про точность оценок — в [docs/07-approach.md](docs/07-approach.md).

## Четыре вещи, которые нельзя сделать как задумано

1. Предоплату нельзя принимать без кассового чека.
2. Условие «предоплата не возвращается» ничтожно.
3. Программный запрет отмены за 24 часа невыполним.
4. Передачу предоплаты врачу при неявке придётся перестроить.

Разбор и ссылки на нормы — в [docs/05-legal.md](docs/05-legal.md).

первый коммит, которым репозиторий создан.

Проверка зависимостей перед каждым обновлением:

```bash
pnpm install
pnpm audit --audit-level=low
```
